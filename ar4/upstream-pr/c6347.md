Another box, and a different shape of workload: **four R9700s at TP=4**, with the split showing up in a way that supports the queue-mapping idea at the end of this thread. Writing out what was and was not controlled.

### Setup

4x Radeon AI PRO R9700 (gfx1201, 0x7551), each on PCIe 5 x16 off a single-socket Threadripper PRO, P2P enabled for every pair. Host kernel 7.0.0-38 with amdgpu-dkms 6.19.14, MES firmware **0x91**, cards capped at 211 W. Inference in the Radiance vLLM image (vLLM 0.27.1, HIP 7.14.60850). Model Qwen3.8-27B int5 (a GDN hybrid: 16 attention + 48 gated-delta-net layers) with a DFlash2 drafter, fp8 KV, `cudagraph_mode FULL_AND_PIECEWISE`. KFD shows 6 queues per worker process at the default limit.

### The split, and what decides it

Two tensor-parallel all-reduce paths, same image, same launcher, same model, fresh container per boot:

| all-reduce path | boots | slow | fast | step (single stream, 8-wide verify) |
|---|---:|---:|---:|---|
| RCCL | 4 | 0 | 4 | 22.3 ms |
| custom one-shot P2P kernel (push into peers' IPC scratch, spin on flags) | 8 | **6** | 2 | **28.4 ms** slow / 18.6 ms fast |

The state is fixed at spawn and held for the life of every process we ran (10 to 20 minutes each). Decode tok/s followed it exactly: 139 / 108 / 125 slow vs 210 / 164 / 191 fast on the same three prompts, with draft acceptance identical. So on this box **which path the process uses for its collectives changes the spawn odds**, which fits the suggestion above that the outcome depends on how the process's streams land on hardware queues at startup.

### What the slow state looks like under the profiler

Same request, torch profiler, FULL graphs, one rank:

| per decode step (median) | fast boot | slow boot |
|---|---:|---:|
| step | 16.8 ms | 26.0 ms |
| GPU busy | 13.5 ms | 15.6 ms |
| GPU idle inside the step | 3.3 ms | **10.4 ms** |
| idle gap before / after each all-reduce kernel (median) | 3.1 / 3.1 µs | **15.2 / 14.7 µs** |
| target GEMM time | 9.42 ms | 9.65 ms |
| all-reduce kernel, mean | 13.3 µs | 19.6 µs |

Kernel durations are the same within noise; the whole difference is the gap after every small kernel, ~1,000 of them per step. That is the same ~15 µs per dispatch that #6685 measures with pending waits on other queues.

Ruled out here: clocks (sclk 3.1 to 3.3 GHz in both states), thermals (57 to 64 °C), runtime PM (forced `power/control=on`, zero resumes during the boot, still slow), drafter behaviour, and the collective kernel itself (38,500 in-situ calls recomputed against RCCL in an eager serve, 0 mismatches, 0 cross-rank differences).

### `GPU_MAX_HW_QUEUES=1`

| | boots | slow | long-pp / prose / code tok/s | 1 / 4 / 8 streams aggregate |
|---|---:|---:|---|---|
| one-shot, flag unset | 8 | 6 | 139 / 108 / 125 (slow boots) | 115 / 345 / 499 |
| one-shot, `GPU_MAX_HW_QUEUES=1` | 2 | **0** | **210 / 164 / 191** | **170 / 448 / 650** |
| RCCL, flag unset | 4 | 0 | 194 / 128 / 157 | 139 / 401 / 608 |
| RCCL, `GPU_MAX_HW_QUEUES=1` | 1 | 0 | 194 / 128 / 157 | 139 / 401 / 608 |

Both flagged boots came up identical to the decimal. On the path that never split, the flag changed nothing at concurrency 1 to 8, so I have no cost to report either, same as the gemma-4-12B result above. It is now the default in our launchers.

A cheap way to tell which state a server is in without a profiler, for anyone running this stack: with a per-step timer around the worker's GPU span, a single-stream step of ~18.5 ms is the good state here and ~28 ms the bad one; the ratio (1.5x) matches the single-card reports.

The 4-rank all-reduce kernel and the launcher change are in a PR to the Radiance repo (jdrews/vllm-mxfp4#2) if the details are useful.
